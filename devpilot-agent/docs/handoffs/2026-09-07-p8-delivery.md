## 已交付能力

- 反馈与候选仅针对 `skills/bug-fix/SKILL.md`，记录 user/session/workspace/project/task/Skill/hash 归因。
- 反馈的任务/项目归因来自可信 nanobot 请求上下文，模型参数必须与其一致；`user_feedback` 记录原始用户消息，不使用模型伪造的反馈正文。
- 候选数据写入现有 DevPilot SQLite 数据库的 `skill_improvement_records` 表，HMAC 根密钥独立存放在数据根之外的用户私有 32 字节密钥文件；候选不会被 SkillsLoader 加载，整个服务数据根及密钥文件禁止 Agent 文件工具读写，数据库不能位于工作区内，数据库迁移为 `0011_p8_skill_improvement_records`。
- 固定评测为 3 类场景 × baseline/candidate × 3 次，共 18 个 case；记录 protocol-level synthetic Agent/Tool trace。它不是实时 LLM 质量提升承诺。
- 激活必须由 nanobot 原生聊天中的直接用户动作触发，确认一次性、5 分钟过期，并绑定 user/session/workspace/project/Skill/版本/测试集/评测结果。
- 激活使用临时文件、fsync、原子替换和 activation journal；重启会对已提交的文件交换进行恢复，journal 完整性异常时阻止新的激活。
- 活动任务使用已捕获的 Skill 快照，新任务读取当前有效版本；恢复前检查外部修改，冲突时停止。
- Dream、普通文件工具和受控模式下的 host shell 都不能绕过 `bug-fix` Skill 的保护；现有 nanobot 前端仍是唯一交互入口。

## 原生聊天使用

在 nanobot 聊天中使用：

```text
/skill-improvement
/skill-improvement <candidate-id>
/skill-improvement <candidate-id> evaluate
/skill-improvement <candidate-id> enable
/skill-improvement <candidate-id> ignore
/skill-improvement <candidate-id> restore
/skill-improvement delete-evidence <evidence-id>
```

`enable`、`restore` 只能由直接用户消息触发；不会创建独立管理页面，也不会自动激活或自动回滚。删除证据同样只能由直接用户消息触发；删除会清除历史原文和引用、保留最小脱敏墓碑，关联候选会失效，不会影响工作区代码。

## 换机边界

另一台电脑先拉取当前分支并安装依赖，再重新配置模型与本机环境。不要迁移或提交 API Key、`.env`、SQLite/私有改进数据、日志、虚拟环境和 `node_modules`；旧机器的确认记录不应跨机复用。用户本地 fixture 改动若仍未提交，必须保留并单独检查，不得当作 P8 实现提交。
