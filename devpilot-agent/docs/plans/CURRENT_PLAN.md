2. 检查分支、HEAD 和工作区修改；保留用户改动。记录当前节点、前置验收记录、

   兼容方式及受影响测试，再在同一批次实施。未知配置不得猜测成功或静默给权限。
5. 执行第 5 节对应节点和第 7 节 review 规则；节点退出条件未满足不能写 complete。

## 1. 产品目标与分工

以 nanobot 为唯一 Runtime，构建用户能理解、维护、扩展并用于比赛/求职的个人
研发 Agent。首版覆盖项目理解、小功能交付和 bug 修复；以 Python 为完整场景，
保留现有 Node/React 支持。已有 DevPilot 是代码交付能力模块，FC 是执行设施。
不以模块数量、工具数量或文档数量衡量完成度。

固定组合：nanobot 原生 WebUI + DeepSeek API（密钥由用户本地提供）+ 阿里云 FC。
沿用已配置的 DeepSeek 模型，记录实际 model ID；不把 Harness 参考源码当模型服务。

| 复用来源 | 职责 | DevPilot 增量 |
|---|---|---|
| nanobot | 模型、Agent Loop、聊天、会话、工具调度、WebUI | 接入现有通道，不再建聊天或第二套 Runtime |
| DevPilot 已有模块 | 变更计划、Diff、确认、应用、记录、回滚 | 补齐真实链路和错误处理，不重新实现 |
| FC | 云端执行环境 | 用现有适配器上传受限快照、运行批准检查、取结果并清理 |
| nanobot Cron / Dream | 已有调度、记忆整理及工作区 Skill 创建/合并 | P8 只补证据、候选验证、确认启用和受控恢复，不重造学习 Runtime |

保留 Python 单体业务层、SQLite 和现有 loopback FastAPI。内部 API/SSE 是适配
机制，不作为独立产品功能继续扩建。DeepSeek Harness 和 Codex Harness 的具体
借鉴与现有 nanobot 能力对照见 [借鉴映射](HARNESS_ADOPTION.md)，不得只写“参考”。

借鉴原则：先验证 nanobot 已有实现；已有能力通过配置/组合满足就直接复用，
只有可复现的任务缺口才补 Python 适配。每项保留“参考路径→实际缺口→落点→
验证结果”；不要求为了凑借鉴数量新增代码，也不运行第二个 Agent Loop。

## 2. 用户流程

项目问答/分析：选择项目 → 提问 → 按需读取 → 给出带文件依据的回答。
复用已有只读工具，无项目写入时不进入修改审批；保持 nanobot 原有正常聊天。

代码任务：
选择本地项目 → 描述任务 → Agent 读取代码并给出提案 → 展开/收起 Diff →
确认执行 → 应用补丁并进行约定的 FC 验证 → 显示结果 → 按需继续修复或撤销。

- 提案只展示目的、文件/改动摘要、验证内容和云端上传范围；详细 Diff 按需展开。
- 用户此前已选择“一次执行包含 Apply 和随后验证”。当前组合操作已实现：服务端在确认时
  绑定同一补丁及检查集合，内部各动作分别鉴权、记录结果；原有单动作授权不能被解释
  成多动作授权。网页中的“执行”映射为受信 `apply_verify`，而 `apply/verify/rollback`
  仍保留为独立兼容动作。
- 没有可用验证后端时，执行前说明并停止组合操作；用户可另选明确标注的“仅应用”，
  结果必须写“未验证”。执行后发生验证故障则保留已应用状态，不自动回滚。
- 修改内容、文件范围或检查集合变化必须重新确认；撤销单独确认，冲突时停止。
- 输出压缩为：改了什么、检查通过/失败/未运行、失败原因、下一步；详情保留日志
  摘要、运行编号和 Diff。禁止向用户堆叠内部哈希、token、状态机名称。

## 3. 必须保留的设计

| 能力 | 简要设计与验收重点 |
|---|---|
| 项目访问 | 明确项目根，拒绝越界/链接逃逸/凭据文件；保留原有大小和补丁限额 |
| 可控修改 | 服务端保存不可变补丁；确认绑定项目、补丁和检查；写前校验原文件哈希 |
| 防重复与撤销 | 一次确认不产生两次副作用；保留前镜像；撤销前校验当前文件未被外部修改 |
| 执行 | 固定检查 profile 由服务端生成请求；模型不能提交任意命令、选择后端或提权 |
| 状态与输出 | 复用现有 Run/事件/结果；只展示持久事实；断线后查询，不重发变更动作 |
| 恢复 | 前端断线不等于服务端进程崩溃；崩溃后定位已有执行，不能确认结果则标未知/失败 |
| 秘密保护 | key 仅在配置/受信后端；上传不含凭据与本机环境，日志/模型结果不含授权 token |
| 权限一致性 | 受控任务中限制内置写文件、exec 及其他旁路工具；用实际工具集合和拒绝测试证明 |
| 候选工具自主性 | 复用 WebUI 已有“默认权限 / 完全访问权限”表达用户被打断的偏好；其精确映射、红线和验收以 `LIVE_HARNESS_EXTENSION.md` 的 H11 为准。它不改变项目 Apply/Verify/Rollback 的独立确认契约。 |

优先使用 nanobot 现有权限/工具配置完成受控任务限制；若配置粒度不够，再做最小
适配并补回归。不得为了复用而开放旁路，也不重写 nanobot 核心循环。

- 本节点仅补未完成的产品接入；已完成的 Diff、审批、事件模块不重写。沿用
  当前实现做一次集成检查，发现阻断后续任务的具体缺口才在对应位置最小修补。
- 用 nanobot 原生 WebUI 和 DeepSeek API 跑通提案、选中修改、确认、拒绝路径；
  真实 FC 未就绪时，执行状态必须如实显示不可用，不能用 Fake 冒充。
- 明确受控任务的工具集合，验证内置写入/Shell 不能绕过确认。
- 复用第 2 节已实现的组合确认契约并完成回归验证，保留已有单动作兼容路径。
- 固定一个 Python 回归测试 profile；定义所需源码/测试快照、依赖模板、超时、
  输出及资源预算。检查项由受信配置选择，项目内配置不能升级权限。
- **退出**：真实聊天提案/确认记录 + 未确认零写入、内容变化拒绝、旁路拒绝测试；
  组合操作授权测试通过。云端验证成功不在本节点冒领。

### P6-02：完成现有 FC 适配器

状态：适配器实现、Fake 契约测试和杭州 FC `provider-default` 真实生命周期证据已完成。
本项目接受该模式作为验证执行后端；网络隔离不属于本项目目标，只保留实际策略标签和透明提示。

**开始条件**：P6-01 的请求/检查约定及相关验收已记录；云端凭据仅在本地。

- 本节点云端测试限开发者明确运行的自有合成 fixture；属于适配器验证，不在产品中
  提前注册为可用后端，不接受模型发起的任意项目验证。
- 只补 `fc_sandbox.py` 和现有执行接口的实际缺口；支持任务标识、超时、取消、
  结果收集、清理及重启后的显式恢复。运行元数据写入脱敏本地快照，服务重启后按原
  `sandbox_id` 调用供应商 `connect`；查不到时才返回未知状态。保留 `run` 兼容入口，按调用需要加方法，
  不为旧计划接口图另建一套执行框架。
- 每次运行一个短生命周期沙箱；上传显式清单及快照哈希，确认的检查在该快照运行。
  测试依赖由开发者预先准备并锁定模板；运行时不自动安装/联网下载依赖。
- FC SDK 内部若需字符串命令，只能由服务端固定 profile 安全编码产生，禁止透传
  模型字符串。接口字段严格拒绝未知参数。
- 网络策略边界：验证请求继续固定为 `network_allowed=False`，但杭州 FC 不支持
  `SessionNetworkPolicy`；`provider-default` 模式不再发送 `allow_internet_access`
  等断网参数，由 FC 使用默认网络策略。结果必须标记 `network_policy=provider-default`，
  不得宣称网络隔离；本项目不以严格隔离作为验收条件。
- 保存 sandbox ID、模板/配置指纹、检查、退出码、时长和脱敏摘要；缺失退出码不能
  默认成功。清理失败另记待处理状态和可重试操作，不能吞掉异常后宣称完整成功。
- **退出**：同一 profile 在 FC 真实跑出通过和失败；超时、取消、清理/跨进程恢复路径有
  实际证据；主机文件无额外改动，费用受时限和单任务并发上限约束。

### P6-03：FC 能力边界与聊天端到端验收

**开始条件**：P6-02 适配器契约验证完成，测试模板与资源预算已固定。

- 按实际 FC 模板验证文件/进程边界、实际策略声明、最小环境、资源限额、输出截断、
  超时取消与清理；本地路径测试不能替代云端能力测试。验证任务本身不请求联网，
  杭州 FC 使用 `provider-default`，适配器省略不受支持的断网参数；项目只记录实际策略，
  不把它扩展为网络隔离保证。
- 能力记录绑定地域/模板/配置/SDK 与验证版本；变化后失效。未知能力视为不满足，
  后端不满足所需能力就拒绝对应执行，不回退本机 Shell。
- 连通性和生命周期证据证明 FC 可作为“验证执行”后端；结果继续标记
  `provider-default`，不宣称断网。项目 allowlist、固定 profile 和显式确认仍是执行边界。
- FC 配置检查通过后，由开发者明确启动本节点的受控验收配置：仅允许已登记的自有
  合成 fixture、固定 DeepSeek 模型、模板/检查和预算；保留聊天确认、全部策略和
  一次性授权。该配置显式标注“验收中”，不对普通项目开放，也不写正式启用标志；
  测试结束关闭。P6-04 的独立人工复核仍是产品启用前提。
- 从真实网页完成两例：小功能通过；bug 失败→提案→确认→FC 回归通过，并演练
  拒绝、撤销冲突、网页重连查状态、服务重启不重复 Apply；FC 运行恢复通过显式
  `sandbox_id` 接管，不创建替代沙箱、不重放命令。补一个 Node/React
  现有 fixture 检查，保留跨栈覆盖但不扩建前端开发平台。
- 自动修复复用原有最多三轮和累计预算；每轮变更仍须明确确认，遇到同类失败、
  基础设施故障或范围变化停止。本版不新建预授权的无人值守模式。
- **退出**：功能矩阵有真实记录；记录真实模型/模板/检查版本及结果，Fake 和真实证据
  分列；在 `provider-default` 口径下启用验证执行，不扩大普通项目范围。网络隔离不在
  本项目验收范围，但结果必须保持透明标记。缺凭据/云能力时记录具体阻断，不伪造完成。
  详见 [P6-03/P6-04 验收记录](../evidence/phase-6/p6-03-04-acceptance.md)。

### P7-01：个人 Agent 的任务组合与上下文

**开始条件**：按路线 P6-04 已结束且记录启用决定；若 FC 阻断，只可先做无执行
的配置/离线测试，不据此跳过 P6 或宣称完整产品验收。

具体分为 A：任务能力组合、B：现有扩展启用/禁用、C：上下文续接；只是本节点的
实施步骤，不新增阶段。配置示例、模块入口及反向用例见
[Harness 借鉴详细设计](HARNESS_ADOPTION.md)。

- 复用 nanobot Skill、Tool registry、Session 和上下文预算机制，使用现有项目分析、
  feature/bug 工作流；不新建发布生命周期、路由框架、记忆数据库或压缩器。
- 借鉴 DeepSeek Harness 的显式能力组合：本地受信配置绑定任务 Skill 和已注册
  工具。先用现有配置/entry point；缺失才补一个小适配。Skill 是任务说明，不能
  授权工具。以开发者修改一份现有 Skill 完成定制为验收，不额外创建第四条工作流。
- 借鉴 Codex 的上下文保留：复用 nanobot 摘要/历史入口，保留用户目标、项目约束、
  当前任务/变更 ID、已完成事实和下一步；大日志按摘要+引用传递。摘要不保存令牌，
  不作为审批凭据；续聊时从已有持久状态核实进度与项目哈希，禁止从摘要重放动作。
- **退出**：同一 Agent 完成项目问答、功能提案、bug 提案；只读场景不误触写入；
  长日志和上下文压缩/会话重开后，保留约束与下一步、不重复已执行变更。
  已有 nanobot 实现满足时，以配置和验证记录交付，不强行改核心代码。

### P7-02：证明定制有效

**开始条件**：P7-01 的配置/适配候选及改动前基线固定，测试项目是独立副本。

- 固定三个小任务：带文件依据的项目解释、一个小功能、一个带失败回归的 bug；
  使用同一模型、输入、预算和 fixture，记录通过/失败、人工介入、耗时及可得用量。
- 对 P7-01 的配置/上下文改进做改动前后对照，使用独立运行数据和项目副本；
  已完成的 P0–P5 保持启用，不能为对照卸掉其安全边界。次数固定记录，失败不删。
- 只读/提案评测不依赖 FC；实际检查仅在 P6 已验收的后端运行。没有测出提升则
  如实写“无已证实收益”，撤去无收益的新扩展，不重构既有模块。
- 本次已验收批次选择离线任务契约评测：固定输入、fixture、profile/config 版本和
  重复次数一致，但不调用模型或 FC；因此结果只证明路由/边界契约，不作 LLM 质量保证。
- **退出**：每项借鉴都有来源、复用/改动说明和实际结果；保留一个 Node/React
  现有 fixture 回归。能解释自己的增量，不能把上游功能写成独立原创。

### P7-03：换机可用与作品集交付

**开始条件**：P7-02 结果已记录，功能范围和已知限制明确，不把评测成功率写成保证。

- 完成必要回归、迁移与备份恢复、密钥/许可证检查；锁文件安装 nanobot + 内部
  控制面，恢复 DeepSeek API/FC 配置并检查缺失提示；本机依赖/缓存继续用 E 盘。
- 一份启动说明说明如何配置模型、改 Skill、接入受信 Tool 和查看任务结果；
  配一份评测结果与简短演示，不增加管理页面。复制参考实现时核验许可证和署名。
- **退出**：换机启动且三个任务可重演；说明哪些来自 nanobot、哪些借鉴 Harness、
  哪些是本项目实现。完整沙箱版要求 P6 通过；P6 阻断时只发布明确标注未验收的演示。

这是基础版交付，不代表 P8 完成；P8-02 在同一份说明和评测材料中补最终交付，
不复制一套安装系统或文档。

### P8：可验证的 Skill 持续改进

完整实施细则、字段语义和反向用例见 [SKILL_IMPROVEMENT](SKILL_IMPROVEMENT.md)。
这是用户本次明确批准的有限扩展，优先于第 8 节旧的工作流排除，但只限以下范围：

| 节点 | 前置 | 最小交付 / 退出 |
|---|---|---|
| P8-01 证据与候选 | P7-03 基础版已交付 | 一个已有 Bug 修复 Skill；反馈归因、项目作用域、未激活候选；Dream/手工/普通工具写入路径受控的拒绝测试 |
| P8-02 对照验证与启用 | P8-01 通过，P6 后端验收有效 | 旧/新版本固定场景对照、原生聊天确认、新任务版本固定、陈旧确认拒绝及恢复演练；未证实收益的候选不启用 |
| P8-03 可选定时批处理（已选择并完成） | P8-02 端到端试点通过且用户选择此扩展 | 已复用 Cron，默认关闭；完成用户配置后的批处理、无新证据不调用模型、不自动激活、预算与重启去重及定时部分使用说明 |

后续模型不得仅凭“继续主计划”改变已记录的选择或扩大 P8-03 范围。

每个节点按第 7 节完成开发双审。产品内每份 Skill 候选是 P8 固定评测+用户确认，
不是为日常每条反馈再启动完整仓库 review；若修改实现或受信规格仍走开发双审。

## 6. 各节点实施细则

本节与第 5 节一起执行，不新增节点。下述源码路径相对仓库根；测试文件先用
`rg --files` 定位现有集合再补用例，禁止重新造一套重复测试目录。

### P6-01 实施细则：把确认变成准确动作

**入口**：`devpilot-agent/src/devpilot/nanobot_tools.py`、`action_broker.py`、
`verification.py`、`control_plane.py`；`nanobot/nanobot/channels/websocket/runtime.py`。
前置只读取 P5 当前验收记录，沿用其成果；不复审 P5 历史 diff。

1. 用自有小 fixture 记录实际“提案→选中→确认→Tool”的调用链，区分 UI 选择、
   Gateway 可信事件、模型参数。先证明调用到现有工具，再修具体断点。
2. 将组合确认绑定用户/会话、项目、ChangeSet、plan/patch/scope 哈希、检查集合与
   profile 版本、输入快照身份、有效期、随机确认 ID。字段映射到现有对象，不另开
   状态库；服务端计算/核实，模型不能签发。任一绑定变化使未消费确认失效。
3. 执行顺序：验证确认和所需能力 → 应用已存补丁 → 记录应用结果 → 在匹配的
   快照上验证 → 记录子结果。应用失败不运行测试；验证失败保留应用事实。
   每个副作用独立幂等键/记录绑定同一组合，重试查询已完成步骤而非再写一次。
4. 确认中不含 token；内部授权仅在受信调用中消费。缺后端时组合执行不写项目；
   用户另行确认“仅应用”可执行既有单动作。撤销仍独立确认，不能从组合推导。
5. 固定 Python 回归检查，明确源码+测试文件、排除项、模板依赖、工作目录、
   超时和现有上限；全快照哈希覆盖测试输入，不能只哈希改动文件。

**必测**：正常组合、未确认、陈旧内容、重复/并发确认、应用失败、验证失败、
后端缺失、不同聊天复用、实际启用工具的旁路尝试。测试断言文件和真实调用次数，
不能只断言模型回复。结果拆分 application/verification，名字沿用实际 schema。
**失败处理**：保留最后确定状态；未知写入状态沿用项目锁定/恢复逻辑；不重新应用。

### P6-02 实施细则：FC 生命周期

**入口**：`devpilot-agent/src/devpilot/fc_sandbox.py`、`execution.py`、`verification.py`、
现有持久化/后端健康路径。先定位现有类与调用者，保留兼容 `run` 入口。

1. 验证地域、endpoint、模板、SDK 依赖和预算配置；错误分类为配置、鉴权、创建、
   上传、执行、超时、取消或清理失败，返回脱敏信息，保留受控详情引用。
2. 创建后尽早保存运行 ID 与 sandbox ID；仅上传获准快照，不挂载宿主目录，
   不复制 `.env`、虚拟环境、凭据或完整进程环境。记录内容哈希与 profile 版本。
3. 在明确工作目录运行固定检查；完整退出码缺失/无法解析时为未知或失败，不能
   默认 0。限制收集/持久化输出大小，注明截断；不只在展示末尾截断超大缓冲区。
4. 超时和用户取消均终止实际执行，再清理沙箱；取消重复调用不产生新任务。
   `finally` 尝试清理，清理失败有独立结果和有界重试/人工处理入口，不能吞掉。
5. 重启恢复按已存 ID 查询供应方状态；已结束取结果，仍运行按已定策略继续观察
   或取消；查不到则标未知。禁止重新创建同一验证来伪装恢复。创建后未拿到 ID 的
   不确定窗口须记录，依靠云端 TTL/可查询标识控制残留，不承诺不存在窗口。

**必测**：通过、非零退出、上传失败、缺退出码、超限输出、超时、取消、重复取消、
清理失败、服务中断恢复。Fake 契约测状态和调用，真实 FC 自有 fixture 测实际行为。
**失败处理**：优先保存执行和清理两个事实；待清理未解决不报告“完整运行成功”，
不得把适配器异常变成测试通过。云端测试保留时限和单任务预算。

### P6-03 实施细则：实测隔离和完整流程

**入口**：现有 FC 配置/能力登记、执行模块和 nanobot WebUI 集成；证据放
`devpilot-agent/docs/evidence/phase-6/`，记录实际候选与模板配置指纹。

1. 每项能力记录“测试方法、预期、实际、证明边界”；涵盖进程/文件、网络能力声明、
   环境、资源、超时取消和残留。`provider-default` 下只记录“任务未请求联网、网络
   隔离未知”；不能把省略网络参数或单次拒绝连接当作隔离证据。若后续测试网络边界，
   目标必须为开发者控制或明确许可的端点，并结合对照排除单纯 DNS/断网。
2. 检查上传排除和越界输入；隔离证据分别说明云端工作区和本机未暴露目录，
   不将字符串过滤器当作隔离系统。资源、取消、清理需有观测结果，未知项不填 true。
3. 能力检查通过后启用第 5 节的受控验收配置，以真实 DeepSeek + 网页完成既定场景。
   保存脱敏关联 ID、补丁和验证结果引用；脚本直接调用 API 不能替代网页确认验收。
4. 在只读/运行中刷新页面验证查询恢复；单独中断服务验证恢复状态与零重复写入。
   两种故障分开记录。演练拒绝、变更后撤销冲突和回滚；文件哈希为断言依据。

**退出明细**：必需能力全部证明、两例主场景+跨栈用例通过、恢复不重复副作用、
用户可理解失败结果；测试与截图只记录实际执行内容。**失败处理**：关闭受控验收，
保留数据/日志摘要和缺证项；不降低所需能力或切换到本机执行求通过。

### P6-04 实施细则：作出启用决定

**入口**：后端登记/能力配置、phase-6 证据、已有运行说明；不新增管理页面。
核对版本/配置与证据一致 → 按第 7 节复用已覆盖范围完成双审 → 独立人工复核 →
记录可启用能力及限制 → 受信配置启用。缺任一步保持不可用。
能力配置改变后旧证据失效，按影响范围重验；不能只修改文档继续沿用旧结论。
启用失败时撤回启用配置，保留已有项目和记录；验证健康失败能阻止新执行。
此节点的审查整合前面已审增量，只审未覆盖集成/新增风险，不重审整个历史仓库。

### P7-01 实施细则：自己的 Agent 怎样定制

**入口**：`nanobot/nanobot/agent/skills.py`、`agent/tools/loader.py`、
`agent/tools/registry.py`、`agent/context_governance.py`、`session/manager.py`；
DevPilot `nanobot_tools.py` 和 `pyproject.toml` entry points。详细语义见 HARNESS_ADOPTION。

1. 对项目分析、feature、bug 三个已有任务列出实际 Skill/Tool 依赖；验证现有
   启用/禁用及任务隔离能力。对应配置足够则直接使用，不创建新插件框架。
2. 受信任务配置固定 Skill、工具集合和输出约定；缺依赖/重名明确错误。
   工具可见和可执行权限分别验证，不能只靠提示词约束。配置变更对新任务生效。
3. 修改一份已有 Skill 验证定制路径；代码扩展只在确有缺口时使用现有 entry point。
   不新增第四条工作流，不改 Agent Loop；只读聊天继续正常使用。
4. 核实已有上下文摘要/截断；补齐目标、约束、业务 ID、完成事实和下一步的组织。
   业务事实重新查询，日志用受限引用；摘要不含凭据，不能作为确认或自动重试许可。

5. 项目上下文先定位入口、相关模块和测试，再按需加载；保存路径/哈希引用而非
   全仓文本。外部文件变化使相关结论待复核；跨项目经验必须带项目身份，不能污染
   其他任务。沿用现有检索与上下文入口，不新建向量库或索引服务。
6. 增加任务级无效循环检测，优先复用已有预算/工具轨迹。指纹包含工具、规范化
   参数、相关输入版本和错误类别；同一错误且无新证据连续 3 次暂停该尝试，最多
   允许 1 次有新假设的诊断分支，总预算不重置。配置/鉴权等确定性故障直接报告，
   网络临时故障仅有界重试；不得把基础设施失败当业务代码问题反复修改。
   正常运行状态查询、不同版本文件复查和预定评测重复不算无效循环。停止后给出
   已知事实、未知项和下一步，不把停止记成功，也不擅自扩大权限。
7. 确定性重复步骤先盘点已有 Tool/脚本；同一步骤在实际轨迹重复出现且易错时，
   才提取最小已有模块内 helper 或已审核脚本。由固定 profile 调用，模型不临时
   生成测试启动命令；没有证据就不加新工具，本节点不增加第四条用户业务工作流。

**必测**：三类任务走对工具、配置缺项、禁用工具被点名、两会话不互相污染、
长日志压缩、会话重开、文件外部修改、结果未知；补测同错循环停止、合理轮询
不误停、诊断预算不重置、项目经验不串用。**失败处理**：恢复上一个新配置，
保留原 nanobot 功能；失败配置不得扩大工具集合“自动兜底”。记录复用和新增的界线。

### P7-02 实施细则：小规模可复现评测

**入口**：现有 fixtures 和相关工作流；新增评测脚本仅在现有脚本无法表达时建立。
固定任务文本、起始文件哈希、模型 ID/参数、预算、template/profile 和配置版本。
将用户真实遇到、可脱敏且可授权重现的问题逐步补入现有 fixtures；保留失败，
记录是否来自真实任务或合成任务。开发样例与保留评测样例分开；待评候选不能改
验收标准。首版仍沿用以下 18 次核心对照，不自动为每条新经验增加昂贵全量运行。
默认每个主任务改动前/后各 3 次，共 18 次；记录实际用量，预算不足时停并注明缺失，
不得降低次数后声称同等统计结论。基线是 P7-01 改动前版本，保留 P0–P5 安全能力。

项目解释以文件引用和预先列出的事实判断；小功能/bug 以固定行为测试、文件范围、
确认与执行事实判断。每次重置的是专门的 fixture 副本，不能重置用户仓库。
结果表字段：任务/版本/次数、成功与原因、人工介入次数、耗时、可得用量、证据引用。
缺模型用量写 unavailable；小样本只能说明本组任务结果，不能推广为通用提升。
**失败处理**：基础设施失败与模型失败分列但都保留；对完成规定评测仍无证实收益的
新扩展按第 5 节撤去，回退仅限本轮新增扩展并补受影响验证，不回滚历史功能。
评测未完成应标未完成，不能据缺失结果声称有效或无效；保留已有可用基线。

### P7-03 实施细则：其他电脑能继续开发和使用

**入口**：README、现有启动/迁移命令、锁文件和运行说明，不增设安装管理产品。
1. 新目录/另一台电脑按记录安装；各项目开发/测试环境隔离，防止并行 `uv` 修改
   同一环境。集成运行时，nanobot 所在环境必须同时安装 DevPilot 包及其依赖，
   使 `nanobot.tools` entry points 实际可发现；控制面可独立进程/环境运行。
   固定并记录集成依赖解析方式，不把只含 nanobot 的环境当作完整部署。
   启动后确认 DevPilot 工具可加载，再记录命令、数据位置、端口、配置名与停服方式。
2. 凭据由用户本地填写，模板只含示例值；缺 key/端口占用/旧库版本要能定位原因。
   验证备份在隔离数据目录恢复，检查运行记录和文件关系，不覆盖原数据。
3. 跑必要回归、迁移、Secrets 和许可证检查；已知无关失败记录原因和影响，不能
   删除失败测试制造通过。复现三项任务，确认配置修改可按照说明完成。
4. 文档用一条结构说明 nanobot、任务能力、FC；展示带边界的实际结果与借鉴来源。
   发布/推送按用户授权进行，交付物不能包含 key、数据库、真实项目日志或环境。

**完成条件**：新环境可启动/停服、既定场景可重演、恢复可验证、来源可说明。
沙箱声明遵守 P6 状态；**失败处理**：回退本次发布配置/版本，不删除原数据。

## 7. 开发与 Review 的可执行规则

本文与 [ADR-0004](../adr/ADR-0004-batched-review-and-incremental-recheck.md) 必须在
每次开发及 review 前读取；下列细则是用户授权的流程约束，优先于旧交接中的
逐修改全量复审习惯。双轴独立审查保留，减少的是重复范围。

### 一次开发批次如何结束

1. 完成一个节点或事先记录的独立验收批次，整理适用测试、证据和文档，再固定 SHA。
   不按文件数/问题数逐个开 review；审查期间不继续修改该候选。
2. 主代理并行派发 Standards/Spec，给出基线、候选、diff、需求段落、已测结果、
   已覆盖范围和明确排除项。审查员首先核对范围，一次汇总本轴有效发现，不递归派发。
3. 主代理合并相同问题引用但保留两轴原结论；给每项问题固定 ID、影响、修复位置、
   验证方法和状态。批量解决全部确认有效的发现，再测试受影响范围。
4. 原审查员检查旧候选→新候选增量和关联风险；无变化部分继承前次审查。升级到
   更大范围必须说明新增风险路径。纯引用/文字修正不重跑运行测试。
5. 两轴无待修复项且对应检查通过后结束该批次。只追加审查结论/状态的记录提交由
   主代理检查，不再为“写下 PASS”开 review；后续若改行为/需求则按新增量复审。

### 哪些情况不能反复扩大 Review

| 情况 | 必须处理方式 |
|---|---|
| 发现实际缺陷/遗漏验收项 | 提供路径、触发条件或违反的条款，批量修复和对应复核 |
| 命名/格式喜好或未来功能建议 | 非规范违例不列为阻塞，不为清零建议扩展本次范围 |
| 重复提出已关闭问题 | 引用原 ID；无新证据沿用原关闭结论，不重新全量审查 |
| 报告缺少候选/测试来源 | 补记录并核对事实；不能要求先伪造 PASS 来解除 pending |
| 工具/网络故障 | 保留已有成果，重试同任务；不换人重扫来冒充通过 |
| 同一问题第二次复核仍未关闭 | 暂停发起下一轮审查，主代理定位根因/最小复现后整批修复 |
| 两轮后仍不断出现不同问题 | 检查遗漏边界、要求变更或范围漂移，先稳定检查表；不盲目加轮次 |

不设“轮数到了就通过”的上限。上述暂停是停止盲目复审，不是停止已授权的修复。
如果只是 reviewer 缺少子代理接口，由主代理提供派发记录澄清，不视为运行阻断。
累计等待 5 分钟未给结果时请求已检查/剩余/阻断摘要；不要催其对未检查部分 PASS。
只有 reviewer 真正失败/失联才替换，并传递旧报告、问题表和未覆盖范围。

### 验证范围与记录模板

DevPilot 行为变化运行受影响 pytest、Ruff/Pyright；nanobot 改动运行对应集成集合；
改 WebUI 时运行受影响前端检查；迁移运行迁移/恢复测试；FC 变化按契约与能力影响
做云端验证。阶段整体验收补必要回归一次；同一 SHA/环境的通过结果可复用。
只有代码/依赖/环境变化、失败或新风险才扩大或重跑，不把旧成功移植到新环境。

每阶段沿用一个节点清单、两个轴的报告和检查记录，不为每个问题新建 final 文档。
记录格式：`节点 | baseline/candidate | 范围 | 实际命令与退出码 | 问题ID/状态 |
reviewer ID/覆盖范围/结论 | 剩余项 | 下一步`。已有字段可直接复用，不造第二套索引。

## 8. 范围与交付纪律

### 每个剩余节点的实施输入与交付

| 节点 | 开发前输入 | 最小交付（在原节点证据中记录） |
|---|---|---|
| P6-01 | 当前工具清单、单动作契约、一个 Python fixture | 确认的数据绑定/组合动作结果、上传清单与固定检查定义；实际 Tool 链路通过 |
| P6-02 | 上项请求/结果契约、用户本地 FC 配置 | 现有适配器生命周期补全、失败/清理结果及现场检查记录 |
| P6-03 | 适配器验证结果、固定模板与预算 | 隔离矩阵和真实聊天成功/失败/恢复记录；声明未通过项 |
| P6-04 | 前述完整证据 | 双轴审查、独立人工复核、明确启用或不可用决定 |
| P7-01 | 已有 Skill/Tool/Session 接口、借鉴设计 | 受信任务配置、必要的小适配或“直接复用”记录、工具隔离及续聊测试 |
| P7-02 | 配置/上下文改进前后版本、同一 fixture 集合 | 同模型同预算的结果表；固定次数、失败和未证实收益如实保留 |
| P7-03 | 已验收版本、依赖锁、本地配置说明 | 换机启动/恢复记录、一个开发使用说明、演示及来源署名 |
| P8-01 | P7 基础版、Dream/Skill 写入入口、一个实际 Skill ID | 来源可追踪的反馈、未激活候选、所有可达写路径受控证据 |
| P8-02 | 固定旧/新候选、受信测试集、预算 | 对照结果、聊天确认/新任务生效/恢复测试；无收益如实不启用 |
| P8-03 | 已通过的手动闭环、Cron 配置与交付材料 | 定时去重和预算测试、默认关闭、更新原有换机说明和实测演示 |

实现顺序固定：检查现有能力 → 记录具体缺口 → 最小配置/实现 → 对应验收 →
批量 review。P6-01 先确定实际字段和默认限额；沿用现值，不在这里另造一套 schema。
组合执行结果必须能区分“应用失败”“已应用且验证失败/未运行”“验证通过”，
不能用单一成功标志掩盖部分完成。节点验收以第 5 节为准，本表补充交付内容。

### 范围控制

不新增独立页面、多用户、第二 Provider/后端、远程 Skill 市场、插件平台、专门
safe-refactor 产品线、知识库/MCP 扩展、定时日报、自动提交部署、微服务或通用调度器。
唯一新增自动化是 P8 已批准的 Skill 改进批处理，复用现有 Cron/Dream；不是自动
发布 Skill、自动修改项目或无人值守代码修复。普通 nanobot 已有定时任务继续保留。
已有辅助模块保留兼容；仅在主流程有明确需求时修改，不启动全仓清理工程。
保留现有修复/安全回归用例，旧 React fixture 仍是测试对象，不是产品页面。

每节点用一条记录写清：目标、SHA、修改范围、实际检查结果、未完成项及下一步。
按 ADR-0004 批量修改→预检→双审→增量复审；不因新证据文档重复全量审查。
最小证据为一份阶段清单、两轴报告和可复现检查记录；不再复制多套 final/manifest。
精简适用于新增工作，不改写已有审查结论，也不以移除门禁让历史失败消失。
