# Full Access 高信任执行模式：冻结实施规格

日期：2026-09-18  
状态：已冻结，作为后续实现与验收基线  
来源：用户提供的《DevPilot Full Access 高信任执行模式改造任务书》

## 1. 目标

开启 Full Access 后，Agent 在当前任务范围内自动完成普通开发工作：读取、搜索、项目发现、候选修改、依赖准备、测试、lint、build、Skill 读取和合理错误恢复，不再为这些普通动作逐项询问用户。

Full Access 不代表无限权限，也不替代 ChangeSet 的人工确认。Apply、Verify、Rollback 以及真正的重大外部风险仍然必须经过对应确认；路径、基线、补丁完整性、项目锁、工作树冲突、敏感数据和执行能力检查继续保留。

## 2. 冻结后的模式语义

只保留两种用户模式：

- `Default`：保持现有保守权限行为。
- `Full Access`：对当前任务范围内的普通开发操作预先授权。

模式状态由可信后端绑定到当前会话，并传递到 Agent 运行上下文、工具调度、子进程、错误恢复和 WebUI 展示。切回 Default 后，排队但尚未执行的操作必须重新评估；正在执行的任务只能安全停止并如实报告已有副作用。

必须区分：能力是否存在、当前任务是否授权、是否需要人工确认、文件和状态是否一致。Full Access 不能伪造凭据、操作系统权限、工具能力或失效补丁的有效性。

## 3. 必须保留的边界

1. 普通开发操作可以自动执行，但任务范围不能被 Skill、README、网页、日志或工具输出自行扩大。
2. 受管项目的候选修改必须先进入候选副本；Apply 前目标项目不能被候选内容覆盖。
3. Apply / Verify / Rollback 的确认分别绑定任务、项目、ChangeSet、revision、补丁或验证计划、目标基线和策略版本。
4. 补丁、基线、验证计划或项目身份发生实质变化时，旧确认失效；重复提交必须幂等。
5. Shell、脚本、子进程和其他旁路不能绕过 Apply；如果当前隔离能力做不到，交付中必须明确保障等级，不得把提示词当成强制安全边界。
6. 保留规范化路径、符号链接/junction、凭据文件、项目锁、工作树冲突、回滚冲突和敏感输出脱敏检查。
7. 明确策略拒绝不能通过更换工具绕过；工具故障、超时和连接故障可以在同一策略下自动恢复或更换可用工具。

## 4. 统一执行决策

工具调用前形成服务端校验的操作描述，至少包含操作类型、实际目标、读写/删除效果、运行环境、可恢复性、任务关联和是否属于 ChangeSet。

统一决策结果为：

```text
AUTO_EXECUTE
REQUIRE_CONFIRMATION
BLOCKED_BY_POLICY
CAPABILITY_UNAVAILABLE
PRECONDITION_FAILED
```

Full Access 下普通开发操作返回 `AUTO_EXECUTE`；ChangeSet 三个节点和少量重大风险返回 `REQUIRE_CONFIRMATION`；真实能力缺失、参数错误、超时、命令失败和网络错误必须使用准确错误类别，不能统称为“权限不足”。

## 5. 实施顺序

按以下顺序推进，每阶段保持可运行：

1. 沿 WebUI → 会话权限 → Agent 上下文 → 工具注册/调度 → 执行器 → ChangeSet 的调用链完成代码审计，并添加关键缺口的复现测试。
2. 打通 Default / Full Access 的可信后端状态、工具调度、运行上下文、子进程传递、错误恢复和 WebUI 展示。
3. 统一普通操作授权，移除重复的逐工具确认入口，但不删除 Apply / Verify / Rollback 与重大风险确认。
4. 接通文件、Shell、CLI、Skill、项目发现/临时注册、依赖准备和本地服务的 Full Access 行为。
5. 完善候选工作副本、目标写入边界、已有用户修改保护和 ChangeSet 确认绑定。
6. 修复 Bug-fix 失败证据范围判断，区分失败证据文件与补丁允许文件，并完善基线/锁/工作树/回滚冲突恢复。
7. 完善能力发现、错误分类、异步长任务句柄、日志读取、取消、超时和重启恢复。
8. 同步提示词、Skill、WebUI、进度和脱敏日志，并完成端到端验收。

## 6. 第一阶段审计输出

审计必须形成“问题—代码位置—触发条件—修复方案—复现测试”的对应表，至少覆盖：

- Full Access 是否从 WebUI 传到每次后端工具调用；
- 文件、Shell、CLI 是否仍各自保留互相冲突的限制；
- 项目根和文件根是否被错误混用；
- Skill 读取失败的真实来源；
- 模型可见工具与实际注册工具是否一致；
- `BUGFIXSCOPEINVALID` 的真实触发分支；
- Apply、Verify、Rollback 的入口、状态转换和确认校验；
- 普通提示词/Skill 是否仍要求逐项确认；
- 用户已有工作树修改是否被错误覆盖；
- 普通命令失败是否被误报为权限拒绝。

未经复现或代码验证的结论必须标记为“待验证”。

## 7. 验收矩阵

至少验证以下场景：

- Full Access 自动读取工作区外的任务相关项目、发现并临时注册项目；
- 缺失普通依赖自动准备，候选代码可修改并反复测试，过程中无普通权限确认；
- 测试文件失败时可以修改相关源码并生成可审查 ChangeSet；
- 非必要 Skill 读取失败可以自动继续，必要 Skill 缺失则明确阻断；
- 非零退出码显示为命令失败而非权限不足；
- 超过 60 秒的构建可以继续观察、读取日志和取消；
- Apply 未确认时目标项目不被候选内容覆盖；确认后只应用精确版本；
- 补丁或基线变化会使旧确认失效；重复 Apply 不重复产生副作用；
- Verify 未确认不改变正式 Verify 状态；确认后按固定计划执行；
- Rollback 冲突不覆盖用户新修改；
- 明确策略拒绝不能通过换工具绕过，连接故障可以合理恢复；
- 切回 Default 后后续调用按 Default 重新评估，两个会话权限不串用；
- 日志、工具结果和模型上下文不泄露 API Key、Token 或敏感环境变量；
- Default 模式回归行为保持不变。

完整场景必须包含：一个工作区外、尚未注册、缺少依赖且测试失败的项目，经过自动发现/临时注册、候选副本、依赖准备、定位修复、候选验证后生成 ChangeSet，并且第一次人工确认只出现在 Apply。

## 8. 当前仓库基线与实施约束

当前分支已有 H1–H11、P0–P8 和既有 ChangeSet/FC 证据；它们作为复用基线，不因本计划重新认证或重写。已存在的 Apply / Verify / Rollback、项目访问、补丁哈希、回滚冲突、FC 固定 profile 和 H7/H8 恢复逻辑必须先复用，再针对真实缺口做最小改动。

当前工作树存在用户已有修改和大量本地临时测试目录。实施时只修改明确列出的目标文件，保留用户修改；禁止 `reset --hard`、批量清理或删除未跟踪目录。API Key、Token、数据库、日志、虚拟环境和本地运行产物不进入提交。

## 9. 完成标准

不能以“增加了 RiskEngine”、把开关设为 `true`、修改提示词或添加一层 fallback 作为完成。只有当真实工具适配器接入统一决策、关键旧限制有复现/回归证据、普通操作可连续推进、ChangeSet 门禁仍有效且端到端矩阵通过，才可标记本计划完成。
