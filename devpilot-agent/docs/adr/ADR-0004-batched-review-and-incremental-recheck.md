# ADR-0004：批量修复与增量复审

## 状态与效力

已采纳。依据用户在本次会话中明确要求提高 review/修复效率，并将现有设定写入
冻结计划执行规则。本 ADR 是冻结计划的开发流程受控修订；原冻结计划保留，
不原地改写。本文对审查调度、修复批次和复审流程优先于既有流程描述；
不改变阶段范围、验收项、权限、安全约束或 Standards/Spec 双轴独立审查门禁。
根 AGENTS.md 将本文列为每次任务必读；适用于 P6 及后续工作和历史节点修复。

冻结计划版本必须以实际读取的文件为准：本机 `E:/codex-local/plans/DEVPILOT_FROZEN_PLAN.md`
标注 2.0.0，而已有 ADR 引用 2.2.0。不得把两者当作已核实的同一版本；
涉及具体需求时记录实际来源及适用 ADR，若缺少所需版本则明确该证据缺口。

## 强制执行流程

执行细则由用户本次要求补全在 [CURRENT_PLAN 第 7 节](../plans/CURRENT_PLAN.md)；
每次开发、修复及审查必须同时阅读该节。它明确了问题 ID、非阻塞建议、第二次
复核仍失败时的根因处理、等待策略、测试复用及记录提交免重复审查规则。
本文保留双轴和真实性原则，后续调度按该细则执行，不再引用旧逐问题全量复审习惯。

1. 主代理在任务开始记录阶段、需求来源、验收项、基线提交和证据路径。
   使用已获授权的计划及仓库上下文确定常规选项，不重复询问已确认事项。
2. 以一个可独立验收的目标为批次。先完成该批次的代码、相关测试、文档和
   证据预检，再固定候选提交；禁止每修复一项就重新全量审查整个阶段。
3. 预检覆盖受影响检查、依赖锁、JSON、引用路径、哈希及其字节规范、真实测试
   计数和命令、当前与历史证据区分。测试使用项目独立环境；不同项目不得并行
   修改同一个虚拟环境。使用实际执行过的锁定命令，不倒改历史测试记录。
4. 主代理向 Standards 和 Spec 两个独立 subagent 并行派发同一基线、候选 SHA、
   diff、需求及标准来源。首次完成适用范围的完整审查；报告分别保存。
   主代理负责调度，两个 reviewer 只负责各自轴，不递归启动下一对 reviewer。
5. 汇总两轴发现并保留来源、严重性、定位与状态；主代理验证问题后一次性修复
   同一批次的有效问题。不同意某项发现时给出证据，请原 reviewer 确认，
   不自行把 FAIL 改成 PASS。
6. 修复后优先复用原两位 reviewer，提供旧/新 SHA、完整累计 diff 的入口、
   修复增量、问题清单和相关验证。复审检查修复及受影响链路；未变化范围
   沿用已完成的审查结论。涉及权限、安全边界、架构、公共契约或无法判断影响
   范围时扩大审查；不因纯文档勘误自动重跑全阶段测试和全量 review。
7. 候选必须可访问且不可变。报告写清首轮完整范围和每次增量 SHA，以及最终
   覆盖的候选；换名、提示“无代码变化”或催促 reviewer 均不能替代实际核对。
8. 两轴对最终候选明确通过、有效问题关闭、适用检查通过后才能标记完成。
   之后仅追加原始结论/验收状态的记录提交，由主代理核对其差异和引用；
   若改变实现、需求或证据内容，重新进入相应增量复审。

## 等待、阻断与证据

- 等待期间完成互不重叠的收尾工作；不因等待而反复启动新 reviewer 或取消
  仍有效的审查。发现任务范围误解时复用原 reviewer 澄清。
- 耗时异常时请求已检查范围、剩余范围和具体阻断；超时或检查不完整必须记录
  为未完成，不能要求 reviewer 基于未检查的内容直接 PASS。
- subagent 工具确实不可用时如实报告审查阻断。成功派发的 reviewer 自身没有
  调度接口不构成阻断；主代理保存两位 reviewer 的 ID 和派发证据即可说明分工。
- REVIEW_PENDING 是结果落盘前的正常状态，不能据此要求先写 PASS 再审查。
- 报告至少包含：reviewer ID/轴、基线 SHA、候选 SHA、检查范围、发现与关闭依据、
  实际测试及限制、最终结论。历史结果不冒充本轮证据。
- 不承诺“只能一轮 review”：目标是减少重复工作，真实缺陷仍须修复和验证。

## 执行示例

完整审查 A → B 发现三项问题；主代理集中修复为 C，运行受影响检查；同一对
reviewer 核对 B → C 和关联风险，分别记录 A → B 的结论加上 B → C 的增量结论。
两轴明确通过 C 后追加报告。没有新代码/需求变化时，不重启 A → C 全量扫描。
