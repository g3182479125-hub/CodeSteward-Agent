# 自然语言确认与思考节点展开设计

## 背景

当前用户确认入口依赖少量精确字符串，例如“执行”“验证”“撤销”。这会把内部协议字段错误地暴露给用户：用户已经明确表达“撤回”或“把刚才的修改去掉”时，系统可能没有识别为回滚意图，随后继续追问固定口令，甚至重复触发同一个待审批动作。

同时，前端已经从流式事件中保存了每个思考节点的完整内容，但界面只展示一行摘要，没有提供节点级的展开入口，用户无法查看该节点完整的过程信息。

本次改动目标：让用户用自然语言表达意图；让内部能力、签名和审批继续严格；让每个思考节点可独立查看全文。

## 目标与非目标

### 目标

- 在用户确认边界识别自然语言意图：应用、应用并验证、验证、回滚、停止、信任项目、启用插件。
- 识别常见否定句和歧义表达，避免误执行；只有必要时进行一次简短澄清。
- 控制面暂时不可用时，明确记录待处理意图，避免重复追问或重复登记。
- 每个思考节点默认显示中文单行摘要，点击后展开完整内容，支持流式更新。
- 为后端、前端和交互状态补齐可回归测试。

### 非目标

- 不取消审批、签名、能力校验、项目锁或回滚保护。
- 不让前端或模型直接生成可信 capability；可信动作仍由后端根据已验证的待确认上下文签发。
- 不把内部 API 的 `apply_verify`、`rollback` 等字段改成自然语言；自然语言只存在于用户入口层。
- 不把“好”“行”“可以”等孤立肯定词在没有明确上下文时当作授权。

## 方案

### 1. 统一用户意图解析层

新增共享的意图解析模块，输入用户当前文本和当前待确认上下文，输出：

```text
intent: apply | apply_verify | verify | rollback | stop |
        trust_project | plugin_confirm | none | ambiguous
confidence: explicit | contextual | none
reason: optional diagnostic code
```

解析流程固定为：Unicode 标点和空白归一化、大小写归一化、否定检测、上下文动作匹配、歧义判定。解析结果只表示用户意图，不等于授权。

典型表达包括：

| 意图 | 自然语言示例 |
| --- | --- |
| rollback | “撤回”“撤销”“回滚”“恢复原版本”“把这次修改去掉” |
| apply | “可以改”“按这个方案做”“开始修复” |
| apply_verify | “改完跑测试”“直接修好并验证” |
| verify | “验证一下”“跑测试确认” |
| stop | “停止”“不继续了”“先到这里” |
| trust_project | “这个项目可以信任”“允许这个项目” |
| plugin_confirm | “启用这个插件”“可以试用这个插件” |

明确否定（例如“先别执行”“只看看不要改”“不要回滚”）优先返回 `none` 或 `ambiguous`，不能被动作关键词误触发。单独的“好”“行”“可以”只有在上一条消息明确询问单一动作且上下文没有竞争动作时才返回 `contextual`。

### 2. 后端接入与安全边界

- WebSocket runtime 使用统一解析结果创建已签名的确认上下文；“撤回”“恢复原版本”等自然语言可以生成内部 `rollback`，但必须仍然匹配当前会话、项目、ChangeSet 和 capability。
- `control_plane.py` 在用户文本边界调用统一解析器；内部 RPC、审批 token、action/capability 字段保持精确枚举。
- `nanobot_tools.py` 的执行、验证、回滚入口复用同一解析规则；如果没有合法的签名上下文，继续拒绝执行。
- 插件授权、项目受信入口复用同一解析规则，去除要求用户输入固定口令的提示。
- 前端不再用固定字符串判断是否携带待确认对象；只要当前消息带有合法的待确认上下文就携带它，最终动作由后端解析和签名。

### 3. 待审批与重复提问策略

当用户已经明确表达动作但控制面不可用：

1. 只登记一次待审批请求，并保存意图和请求上下文。
2. 返回“已记录你的撤回/执行意图，等待审批服务恢复”，不要求用户再次输入同义词。
3. 当前轮次进入终态，不继续重复调用同一个失败动作。
4. 控制面恢复后，沿用已登记请求继续处理；在此之前不得把 `approval_pending` 说成已完成。

如果消息没有明确动作或同时包含互相冲突的动作，只追问一次：“你希望我执行、验证，还是撤回这次修改？”不再要求用户记忆系统内部固定词。

### 4. 思考节点展开交互

`ReasoningRow` 在保留现有时间线和外层任务折叠的前提下增加节点级 disclosure：

- 折叠态：中文单行摘要、执行中/已完成标记、展开箭头。
- 展开态：当前节点的完整 reasoning 文本，保留换行并自动换行；内容较长时在节点内部滚动。
- 每个节点有独立的 `expanded` 状态，展开一个节点不影响其他节点或外层任务折叠。
- 流式期间继续累积并刷新完整文本；用户已展开时不退回单行截断。
- 使用 `aria-expanded`、`aria-controls` 和键盘可操作按钮；点击节点控制器不冒泡到外层折叠容器。
- 节点结束后保留全文，状态图标从运行中切换为完成态。

### 5. Skill 与用户文案

bug-fix、feature-delivery 以及相关用户提示改为：等待用户明确表达对应意图，系统支持自然语言；只有语义冲突或不完整时澄清。内部工具调用仍使用结构化 action，不在用户界面展示“必须输入某个固定短语”的要求。

## 测试与验收

### 后端

- 意图别名表覆盖全部七类动作。
- 否定句、引用代码中的动作词、互相冲突的动作返回拒绝或歧义。
- “撤回”“恢复原版本”可以生成 rollback 的可信确认上下文。
- 无待确认 ChangeSet、项目不匹配、签名失效时仍然拒绝。
- 控制面不可用只登记一次，不产生重复追问状态。
- 停止、执行、验证、信任项目、插件授权自然语言回归测试。

### 前端

- 思考节点默认只有一行摘要。
- 点击单个节点可以展开完整 reasoning，换行内容完整显示。
- 多个节点可以独立展开和收起。
- 流式追加内容时摘要和展开内容同步更新。
- 完成态、空内容和长文本显示稳定，外层任务折叠行为不回归。

### 集成检查

- 后端 lint/pytest。
- WebUI 单元测试、类型检查和生产构建。
- 用自然语言完整走一遍：发现问题 → 提案 → “按这个方案修好并跑测试” → 审批等待/执行 → 结果展示；再走一遍“撤回/恢复原版本”路径，确认不会重复追问。

## 风险与回滚

- 语义识别过宽可能误授权，因此所有结果都必须绑定当前待确认上下文，且否定优先；低置信度只进入澄清。
- 前后端重复解析可能产生不一致，因此前端只传上下文，后端作为唯一可信解析源。
- 旧客户端可能仍发送固定词，固定词继续作为别名兼容。
- 若新解析器造成回归，可单独回滚意图模块和 UI disclosure，不影响既有签名与审批数据。
